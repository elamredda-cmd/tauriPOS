Findings, in priority order

P1 · CONFIRMED DOJO-01 — Unreadable Dojo settings can silently become manual card

Checkout selects Dojo only when its configuration is both enabled and ready. Failed or unfinished configuration reads are not retained as a checkout blocking state. This can expose Confirm Card Payment and take the ordinary card-sale commit path without sending a payment to Dojo.

Current native QA: the exact original public configuration file was recoverably preserved, then a temporary malformed public config was loaded after a cold WebView reload. The existing £11 mock trolley switched from Dojo to Card; selecting Card exposed an enabled manual-confirmation button and external-approval instructions. Confirmation was not clicked; no new order or provider charge was created. The original configuration was restored by moving back the preserved file. Secret files were untouched.

A separate one-shot read fault was armed, entered and rejected, but a later successful read repaired the provider state. That one-shot observation alone does not prove persistent failure handling is safe. The isolated VM fixture additionally exercised the actual commit branch with spies, showing a plain card sale and commitSale, with no Dojo payment call.

Recommended fix: block card submission until current settings are known; retain explicit loading/read-error/unavailable state; allow manual card only after both provider settings have successfully loaded and are intentionally disabled. Customer-account collection already has the stronger unavailable/read-error distinction.

Source: src/routes/+page.svelte:454, :471, :1260, :4613, :4875. Safer comparison: src/routes/customers/+page.svelte:234. Test: src/lib/dojoCheckoutAvailability.audit.test.ts. No production fix applied.

P2 · SOURCE + FIXTURE DOJO-02 — Overlapping recovery can omit Dojo

One global recovery promise is returned to overlapping callers even when the second caller requests a different provider. Checkout starts SumUp and Dojo recoveries concurrently, so the Dojo call can receive a SumUp-only result without its journals being scanned.

This can delay recovery and produce misleading provider-specific feedback. The layout's all-provider sweep every 60 seconds mitigates permanent stranding; this is not a demonstrated lost payment. The actual extracted recovery function reproduced the omitted scope.

Recommended fix: drain the union of requested providers, or consistently perform an all-provider sweep; report only providers actually inspected.

Source: src/lib/terminalRecovery.ts:966, checkout src/routes/+page.svelte:1261, periodic mitigation src/routes/+layout.svelte:122. No production fix applied; not independently native-reproduced.

P3 · DOCUMENTATION DOJO-03 — Timeout instructions are stale

The older testing guide describes automatic sandbox timeout cleanup as removed. Current checkout and customer-account collection both pass the guarded sandbox-cleanup callback; the monitor can use it for a Sandbox, Expired session with an unused Created intent, and then checks fresh provider finality. Live and Unknown credentials are excluded from that automatic branch.

Recommended fix: align current operator/UAT guidance with the intended policy and distinguish sandbox cleanup, live administrator receipt review and historical test records. The old documents were preserved unchanged.

Source: docs/DOJO_TESTING.md expired-payment guidance; src/lib/dojoSessionFlow.ts:209; both route callbacks. No documentation correction applied outside this new audit report.

Official guidance checked on 13 October 2026

The PAC guide separates terminal-session progress from the final payment-intent check, and restricts terminal cancellation after card presentation. A cancel request therefore cannot promise that an already-attempted payment will stop.

The signature guide describes an 80-second operator decision window and provider auto-accept after no decision; the app must still follow the final payment result.

The PAC go-live checklist requires at least one API refund method. This app has a payment-intent refund implementation, but historical provider rejection is not evidence of successful refund capability. Agree the applicability of unoffered checklist features with Dojo and obtain their witnessed approval.

The terminal-state guidance treats expiry as an unresolved result requiring operator clarification; payment-intent cancellation applies to unused Created intents. Neither an Expired session nor a Created portal label alone proves that the customer was not charged.

This report is an engineering audit, not Dojo certification, a settlement statement, or evidence that every Dojo feature works. Current sandbox outcomes are appended only from explicit observations; pending cases remain unverified. Production source was left unchanged.
